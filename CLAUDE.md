# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install
npm run dev       # Vite dev server at http://127.0.0.1:5173/
npm run build     # tsc (type-check, noEmit) + vite build -> dist/
npm run preview   # serve the production build locally
```

There is no test suite, lint script, or CI config in this repo. `npm run build` is the closest thing to a correctness gate (TypeScript strict mode via `tsc`, then the Vite bundle). There is no single-test command to run since no test runner is configured.

Node version is pinned via `.nvmrc` (24).

## Branches

- `main` — the deployed frontend-only app (this is what's normally checked out). Pure React/Vite SPA, with a single deliberate exception: `api/tess-chat.ts`, a minimal stateless Vercel Serverless Function that proxies the AI assistant's default TESS credentials (see the `tess.ts` bullet below) — no database, no auth, no other backend surface.
- `SaaS` — active development branch adding a backend (`api/` — Vercel serverless functions for auth, Stripe billing, SQLite/libSQL via `api/utils/db.ts`), a landing page, and account management on top of the same analysis engine. Substantially diverged from `main` (auth hooks, `AuthPages`, `AccountPanel`, `LandingPage`, Stripe webhook/checkout/portal routes). Check which branch you're on before assuming the backend exists.

`seed_local.ts` (gitignored) is a local-only DB seeding script tied to the SaaS branch's backend; it references `./api/utils/db.js` which does not exist on `main`.

## Architecture (main / frontend core)

This is a client-side balancete (accounting trial balance) analyzer: PDFs are parsed and analyzed **entirely in the browser** — no file ever leaves the user's machine. That "local processing" guarantee is a product requirement, not an implementation detail; don't introduce a server round-trip for the PDF/analysis pipeline without treating it as a breaking change to the value proposition (see `LocalProcessingDoc.tsx`, `DataSecurity.tsx`, `PrivacyPolicy.tsx`).

Data flow: `Dropzone` → `useFileProcessing` hook → `parserClient.ts` → **`parser.worker.ts` (Web Worker)** → `parser.ts` → `reports.ts` / analysis builders → `types.ts` shapes → rendered by `CompanyOverviewCard` / `CompanyCard` / `SummaryCards`, and separately summarized for `ChatbotFab`.

**The whole parse pipeline runs off the main thread.** `useFileProcessing` never imports `parser.ts` directly — it goes through `createParserClient()`, which posts the `File` to a dedicated worker and gets a `CompanyReport` back (both are structured-cloneable, so there's no manual serialization). Two consequences worth knowing before you touch this:
  - **`parser.ts` and everything it imports must stay DOM-free.** It only depends on `pdfjs-dist`, `types.ts`, `format.ts` and `balance.ts` today. (The `document` variable inside `parsePdfFile` is pdf.js's `PDFDocumentProxy`, not the browser's.) Importing anything that touches `window`/`document` breaks the worker at runtime, not at build time.
  - **Cancellation works by terminating the worker** (`parserClient.cancel()`), which is the only reliable way to stop CPU-bound parsing mid-file; the client transparently recreates the worker on the next `parse()`. In-flight promises reject with `ParseCancelledError`.
  - `parserClient` falls back to parsing on the main thread if `new Worker(...)` throws. That fallback is why `yieldToBrowser()` still exists in `parser.ts` — it's a no-op inside the worker (`typeof window === 'undefined'`) and only matters on that path.

- **`src/utils/parser.ts`** — the core engine. Uses `pdf.js` to extract positioned text items per page, regroups them into logical lines (`groupItemsIntoLines`), then parses Brazilian-formatted accounting lines (account code, name, previous/current balance, debit/credit) with regexes tuned to real balancete layouts (`accountRegex`, `moneyRegex`, `cnpjRegex`, `companyCodeRegex`). From the parsed `LedgerLine[]` it derives:
  - `invertedRows` — asset accounts (`1.*`) with credit nature or liability/equity accounts (`2.*`) with debit nature (excluding known dual-nature accounts like `1.2.05.007`, `2.4.13.004`).
  - `zeroMovementRows` — accounts with zero debit and credit movement.
  - `comparisonReport` — cross-checks distribution vs. result accounts.
  - `analysisReports` — 16 fixed rule-based analyses (`AnalysisKind` = `analysis1`..`analysis16`, e.g. CMV x Receita, depreciation pairing) built in `parser.ts` and wired into tabs/labels/export in `reports.ts`. `analysis1`-`12` match by a fixed `Cod. R.` (a classification code separate from the account code, e.g. `142` for Cliente PF) **and, where collision risk exists, the account name too** — `analysis13` learned this the hard way: matching Cod. R. 29/30 alone false-positived on unrelated accounts (Intangível/Custo) in `balancetes/BALANCETE_FICTICIO.pdf`, because that synthetic file assigns Cod. R. sequentially to its filler accounts. `analysis14`/`15` only evaluate on balancetes whose period ends in December (`isDecemberClosing(period)`, exported from `parser.ts`) — anything else returns a neutral "não aplicável" report, never an "attention" or "ok" verdict, since the check is meaningless outside a year-end close. `analysis15`/`16` match by **normalized account name** (`normalizeForCompare`), not by Cod. R. or account code — a 16-file survey of `balancetes/` found those identifiers vary across the different chart-of-accounts templates this office's clients use (e.g. "empréstimos a sócios/terceiros" appears at account `1.2.01.013` *or* `.014`, under at least 3 different Cod. R. values), while the account name stayed the reliable signal.
  - `unclassified` lines and `errors` are kept so users can see what the parser couldn't confidently interpret — never silently drop unparseable lines.
  - **Every raw line lands in exactly one bucket.** `extractLedgerLines` splits `pageLines` into `rows` (ledger), `structuralLines` (recognized report furniture: page header block, closing totals, signature) and `unclassified` (genuinely not understood). The invariant `rows + unclassified + structuralLines === pageLines` holds and is covered by a test — if a future change drops a line silently, that test fails. `unclassified` is therefore a *meaningful* alarm: it drives the "ATENÇÃO ESTRUTURAL" card, the per-company alert badge and the Gemini summary, so noise there directly misleads the user (it used to report 1002 header lines across the sample files when actual data loss was zero).

  Two invariants in this file are load-bearing and easy to break:
  - **Never let two separate pdf.js text items merge into one number.** `groupItemsIntoLines` joins items without a space when the horizontal gap is ≤ 12, but pdf.js sometimes reports a `width` that overruns the next column, producing a *negative* gap between genuinely separate cells. In person-type accounts the CPF sits immediately before the balance, so this silently glued them (`"...OLIVEIRA 01504106466"` + `"0,00C"` → `015041064660,00C`, and `"…45"` + `"1.530,00C"` → `451.530,00C` — a 295x overstatement). `standaloneMoneyRegex` guards this: a text item that is itself a complete money value never gets concatenated onto a trailing digit.
  - **`ledgerBalanceMismatch` (in `balance.ts`) is the tripwire for column misalignment.** `parseLedgerLine` takes `moneyMatches.slice(-4)` as the four columns, which goes wrong whenever a stray number leaks in from the name. Every parsed row is checked against `saldo anterior + débito − crédito = saldo atual`; failures set `LedgerLine.balanceMismatch` and surface as a `CompanyReport.errors` entry rather than being dropped. Across the sample balancetes in `arquivos_de_exemplo/` (gitignored, count varies as files are added/removed locally) the expected count is **0** — if a change makes that number non-zero, it has broken column extraction. Watch the sign convention: this check treats debit as positive, the *opposite* of `signedCurrentBalance`.
  - **`cnpjRegex` and `anonymize.ts`'s `documentNumberRegex` accept the alphanumeric CNPJ format** the Receita Federal started issuing in 2026 (12 leading characters can be `A-Z` or digits; only the 2 trailing check digits stay numeric). Both must be widened together — `cnpjRegex` only affects display, but `documentNumberRegex` is the privacy safety net before the AI payload, so missing this format there means an alphanumeric CNPJ would leak unmasked.
- **`src/types.ts`** is the shared contract between the parser, the report builders, and every component that renders results (`CompanyReport` is the central object passed around the whole app).
- **`src/utils/reports.ts`** builds the human-facing tables/columns (`balanceColumns`, `comparisonColumns`, `depreciationColumns`) and drives PDF (`jsPDF`) / Excel (`xlsx`) export from the same `CompanyReport` data. Build and save are split: `buildPdfBytes`/`buildXlsxBytes` return bytes (used by batch export), `downloadPdf`/`downloadXlsx` save a single file. `reportFileName` includes the period so several months of the same company never collide. `companyHasAlerts`/`companyAlertCount` are the single definition of "company with alerts", shared by `CompanyOverviewCard` and the batch export selection.
- **Batch export** (`src/utils/batchExport.ts` + `ExportModal.tsx`, opened from "Baixar relatórios" above the company cards): the user picks companies (default: only those with alerts; "Todos" is a preset that just changes the checkboxes) and formats, and everything is zipped in the browser with `fflate` — a ZIP instead of N downloads because browsers block multiple automatic downloads. A company with no occurrences still exports (XLSX gets a "Sem ocorrencias" sheet, since SheetJS throws on a workbook with zero sheets).
- **`src/utils/tess.ts`** — optional AI assistant, and **the only code path in the whole app that sends data over the network**. Calls the TESS AI OpenAI-compatible endpoint (`.../agents/{agentId}/openai/chat/completions`) using a fixed, carefully-worded Portuguese system instruction (severity classification, `[Fato]/[Inferencia]/[Hipotese]` tagging, mandatory response sections, a required "Ação recomendada" line per finding). Never sends raw PDF/ledger data — only a compact summary built by `summarizeReportsForPrompt`. Two transports, chosen per-call in `generateTessChatReply` based on whether the visitor supplied their own credentials:
  - **Default (no key from the visitor):** `requestTessViaProxy` posts to `/api/tess-chat` — `api/tess-chat.ts`, a Vercel Serverless Function that holds the Barreira & Associados TESS credentials server-side (`TESS_API_KEY` / `TESS_WORKSPACE_ID` / `TESS_AGENT_ID`, **no** `VITE_` prefix, set in the Vercel dashboard, never bundled to the client) and forwards the already-pseudonymized `messages` array as-is. It's a stateless pass-through (no logging, no storage) with a best-effort in-memory per-IP rate limit and a payload-size cap — not a real defense against a determined abuser hitting the endpoint directly (bypassing the UI/consent entirely is possible; there's no auth layer on `main` to prevent it), just a deterrent against trivial bot abuse.
  - **BYOK override:** if the visitor fills in their own API key + Workspace ID + Agent ID in `ChatbotFab`'s config panel (`hasOwnTessCredentials()`), `requestTess` calls the TESS endpoint directly from the browser instead, same as before this proxy existed.
  - Calling either path requires a TESS Agent pre-created in the TESS Agent Studio dashboard — for the default path that's Barreira's own Agent (env-configured); for BYOK it's whatever Agent the visitor's own key/workspace point to.
  - Because this is the one place the "local processing" guarantee is qualified, several invariants must hold together — changing any one of them silently makes the privacy copy in `PrivacyPolicy.tsx` / `DataSecurity.tsx` / `LocalProcessingDoc.tsx` false:
  - **Consent gate.** Nothing is sent until `hasTessConsent()` is true (set via the checkbox in `ChatbotFab`'s config panel) — `isTessEnabled()` is just this check now, since a working default (the proxy) always exists once consent is granted. No consent ⇒ local mode + `buildLocalFallbackNotice()`. Own credentials saved but no consent ⇒ `buildConsentPendingNotice()`. Never bypass this client-side gate (note it's UX-only — the proxy itself can't verify consent was actually granted, see above).
  - **Pseudonymization.** Everything outbound goes through `src/utils/anonymize.ts`: company names become `Empresa N` aliases, CNPJ/CPF are stripped entirely, and `stripDocumentNumbers` is a final safety net over the assembled prompt. Chat history is re-anonymized on each turn (replies are stored de-anonymized), and the model's reply is passed back through `deanonymizeText` before display. Account codes/names, balances and alerts *are* sent — that's disclosed in the UI, don't quietly widen it.
  - **Own API key storage.** Persisted in `localStorage` as `{ value, savedAt }` with a 30-day TTL (`TESS_API_KEY_TTL_DAYS`); `getStoredTessApiKey()` deletes it once expired. Workspace ID and Agent ID are stored as plain strings (no TTL — not secrets, just routing). These three fields are optional now — `handleSaveApiKey` in `ChatbotFab.tsx` requires all three or none (partial BYOK credentials are rejected).
  - **`VITE_TESS_API_KEY`/`VITE_TESS_WORKSPACE_ID`/`VITE_TESS_AGENT_ID` are dev-only** (`getBuildTimeApiKey()`/`getBuildTimeWorkspaceId()`/`getBuildTimeAgentId()` return `''` unless `import.meta.env.DEV`) — purely a local-dev convenience for the BYOK path, unrelated to the server-side `TESS_*` vars above. Any `VITE_*` value is inlined in plaintext into the public bundle at build time, so honoring it in production would publish the key to every visitor.
- **`src/utils/anonymize.ts`** — the pseudonymization layer described above. Both replace passes sort by length descending so a longer name/alias is substituted first (otherwise `ACME LTDA` would eat part of `ACME COMERCIO LTDA`, and `Empresa 1` would corrupt `Empresa 10`).
- **`src/utils/chatbot.ts`** provides canned suggestion prompts and the local (non-AI) fallback replies. It must not import from `tess.ts` — `ChatbotFab` passes the raw user message to `generateTessChatReply`, which builds the prompt exactly once. (An earlier `buildLocalPromptForGemini` wrapper caused the balancete summary to be embedded twice per request — same pitfall to avoid here.)
- **`useFileProcessing` hook** (`src/hooks/useFileProcessing.ts`) owns all file/report state for `App.tsx`: dropzone drag state, dedup of already-added files (by name+size+lastModified), sequential per-file processing with progress (`processingIndex`/`processingPercent`), cancellation (`cancelProcessing`), and clearing state. Holds one `parserClient` per hook instance, disposed on unmount. The reentrancy guard uses a ref, not the `isProcessing` state — inside `processFiles` the state still holds the previous render's value.
- **`App.tsx`** is a thin shell: sidebar navigation between `main` / `dre` / `privacy` / `security` / `docs` views (the `View` union lives in `types.ts`, imported by both `App.tsx` and `Sidebar.tsx` so it's defined in exactly one place), lazy-loads the heavier secondary views and the chatbot FAB (`React.lazy` + `Suspense`) to keep the initial bundle small, and computes the top-level summary counts (`buildResultsSummary`) from `CompanyReport[]`. The `dre` view owns its own parallel file-queue/report state via `useDreProcessing()` (see below) — it does not share `useFileProcessing`'s state.
- Styling is Tailwind with a custom design-token system in `tailwind.config.js` / `src/styles.css` (CSS variables for light/dark themes, custom spacing/typography scale like `gap-xl`, `font-display-lg`) rather than ad hoc utility values — reuse existing tokens instead of inventing new spacing/font classes.
- `vite.config.ts` manually chunks `react`/`react-dom`, `pdfjs-dist`, `xlsx` and `jspdf`/`jspdf-autotable` into separate bundles — keep this in mind if adding new heavy dependencies (consider adding them to `manualChunks` too). The worker gets its own bundle automatically (`parser.worker-*.js`, ~385 kB with pdf.js inlined); the main thread's `pdf-*.js` chunk is now only fetched if the worker fallback triggers. Compression uses a **single** `compression()` instance with `algorithms: ['gzip', 'brotliCompress']` — registering one instance per algorithm also works but makes each re-emit the other's output ("overwrites a previously emitted file" spam).

## Architecture (DRE — segundo tipo de documento, paralelo ao balancete)

Besides balancetes, the app also parses **DRE** (Demonstração do Resultado / income statement) PDFs — a structurally different document: no account codes, just a results cascade (Receita Bruta → Deduções → Receita Líquida → Custo → Lucro Bruto → Despesas Operacionais → Resultado → Provisões → Lucro do Exercício) with up to N period columns (months) plus Total/%/Média/Média-ano-anterior. This was added as a **deliberately parallel, non-generalized implementation** — separate types, hook, parser, worker-client and rendering components — rather than generalizing the balancete pipeline, since the balancete code is battle-tested/in-production and the two document shapes have little in common beyond "PDF with a money table."

- **`src/utils/dreParser.ts`** — the DRE engine (mirrors `parser.ts`'s role, but a separate file). Key technical fact that drove the whole design: **pdf.js's text-stream order does NOT preserve the DRE's visual left-to-right column order** (unlike balancete lines, which stream mostly in order) — e.g. a line can arrive as `fev, Total, %, [nome], jan, Média-ano-anterior, Média, mar, abr`. Each value item, however, always arrives as one complete, right-aligned text item with a very stable right edge (`x + width`) within its column (<0.1pt variance, since the export uses a tabular font). `findColumnAnchors` exploits this: it calibrates column positions **per file** (not hardcoded pixels) by locating the header line containing exact-match `Total`/`%`/`Média` items plus a `Média <ano>` regex match, then `extractDreLinesFromPage` matches every subsequent money-shaped item to the nearest anchor within a 6pt tolerance (neighboring columns are ≥29pt apart in the sample file, so this never confuses adjacent columns). Reuses `extractPageItems`/`bucketItemsByLine` — exported from `parser.ts` specifically so `dreParser.ts` doesn't duplicate the pdf.js extraction/line-bucketing logic.
  - A line only becomes a `DreLineItem` when it has a label (text left of the first numeric column) **and** at least one value matched to a known column and shaped like money (`moneyLikeRegex`) — this is what silently filters out headers/footers/metadata ("Empresa:", "CNPJ:", "Data e Hora da Impressão") without needing a bespoke pattern per kind of noise.
  - `extractDreMetadata` scans **all** lines before returning company name/CNPJ — "Empresa:" and "CNPJ:" sit on different Y-line-buckets in the real file, so an early return on the first match found loses whichever field comes second (this was an actual bug, caught by the test suite).
  - `dreFormulas`/`buildWaterfallAnalysis` recompute each cascade subtotal from its components and flag any mismatch — the DRE equivalent of `ledgerBalanceMismatch`, matching lines by `normalizeLabel` (NFD-decompose + strip `\p{Mark}` + uppercase) since accent usage is inconsistent across real files (e.g. "PROVISÔES" vs "PROVISOES").
  - Four analyses ship in v1 (`buildWaterfallAnalysis`, `buildVariationAnalysis` — top-10 month-to-month % changes, `buildMarginsAnalysis` — Bruta/Operacional/Líquida over Receita Líquida, `buildMissingComparisonAnalysis` — flags Média/Média-ano-anterior columns that exist but are all-zero), all returning the generic `DreAnalysisReport { rows: DreAnalysisRow[] }` shape (`DreAnalysisRow = { label, cells: Array<{ header, value }> }`) so one generic table component renders all four despite their very different structures.
  - Validated against exactly **one** real file (`acompanhamentos/MEDICAR.pdf`, gitignored) — treat the column-anchor calibration and the variation-analysis top-N/thresholds as a starting point, not something already proven across DRE layout variants (different period counts, different export tools, etc.).
- **`src/types.ts`** — `DreReport`/`DreLineItem`/`DreAnalysisReport`/`DreAnalysisKind` are new, isolated types, **not** extending `CompanyReport`/`AnalysisKind`/`ReportKind` (the two document kinds aren't meant to share a shape).
- **One shared worker, not a second one.** `parser.worker.ts` routes between `parsePdfFile` (balancete) and `parseDreFile` (DRE) via a `kind: 'balancete' | 'dre'` field added to `parserProtocol.ts`'s request/response types — a second worker would duplicate the ~385 kB pdf.js bundle Vite already builds once. `src/utils/dreParserClient.ts` (`createDreParserClient()`) is a sibling of `parserClient.ts` with the same worker-lifecycle/cancellation logic, sending `kind: 'dre'` and pointing at the *same* `parser.worker.ts` URL.
- **`src/hooks/useDreProcessing.ts`** is a sibling of `useFileProcessing.ts` (same queue/dedup/progress/cancel mechanics), deliberately not generalized into one hook — same call: mixing balancete's in-production hook with a second use case wasn't worth the risk for one extra consumer. One real difference: it exposes `totalErrors` (`reports.reduce((sum, r) => sum + r.errors.length, 0)`) instead of balancete's `totalUnclassified`, since `DreReport` has no `unclassified` concept.
- **Rendering** — `DreOverviewCard`/`DreCard`/`DreTable` are parallel components (not configurable variants of `CompanyOverviewCard`/`CompanyCard`/`DataTable`), because `DataTable` hardcodes the balancete's 8 columns in its `<thead>` and sort logic. `DreCard` shows a "Linhas da DRE" tab (raw `DreTable`, columns built from `report.periods`/`report.previousYearLabel` since the period count varies per file) plus one tab per analysis, rendered generically from `DreAnalysisRow[]`. `Dropzone` gained optional `title`/`description` props (defaulting to the balancete copy) so the DRE flow doesn't show "Arraste seus balancetes para cá".
- **`src/utils/dreReports.ts`** — `downloadDreXlsx`/`downloadDrePdf`, mirroring `reports.ts`'s export pair but building columns dynamically from `report.periods` instead of the balancete's fixed column set.
